## Current implementation

The current build contains the dependency-free four-service Node.js kernel:

- **Gateway** authenticates principals, validates requests, applies abuse and
  idempotency controls, and exposes versioned user/operator APIs;
- **Hypervisor** normalizes intent, composes deny-dominant policy, revalidates
  machine authority, constructs explicit plans, checks approvals, and issues
  short-lived single-use grants;
- **Sandbox** executes only the bounded operation named by a valid grant and has
  no ambient supported authority for arbitrary code or external networking;
- **Grid** stores encrypted transactional state, approvals, governance,
  portability, recovery data, and signed hash-linked evidence.

The machine-readable capability registry currently tracks 49 capabilities: 31
implemented, 3 experimental, 2 specified, 9 adapter-required, and 4 disabled.
The registry, not this file, is authoritative for runnable capability status.

### Built but production-unreachable intent primitives

The current source also contains a safe dynamic-input resolution chain for a
future repository-document remediation path. It is deliberately **not** a
runnable production capability.

The merged core can:

1. start from fresh `axiom-intent-execution-eligibility.v1` state that declares
   executor input unresolved;
2. verify an independently signed repository plan under the exact declared
   resolver repository/base/path/lifetime ceiling;
3. produce content-addressed input-resolution and resolved-handoff evidence;
4. derive strict resolver admission facts;
5. require independent implementation-conformance and security-authority
   reviews before producing a promotion candidate;
6. package an exact-one-mapping registry addition without applying it;
7. independently observe exact registry installation bytes without treating
   that observation as authority;
8. re-evaluate the resolved target action through the ordinary policy,
   confirmation, and independent-approval gates;
9. bind the exact resolved input, plan, policy, capability, registry, build and
   authorization state to a prepared repository effect; and
10. source the named approval over the authenticated Hypervisor-to-Grid channel
    and atomically commit `approval.consumed` followed by
    `external.effect.prepared`, so a race/replay loser cannot leave a durable
    prepared effect.

Production reachability remains closed: the production executor registry is
empty, production policy contains no `repository.docs.pull-request.create`
action, no public/runtime route invokes the coordinator, the repository
operator is not called, no external effect executes, and no merge occurs.

### Agent Runtime Adapter v1 boundary

The candidate Agent Runtime Adapter v1 contract is byte-pinned at version
`1.0.0`. The required verification path checks its schema and retains a
commit-bound artifact from a 28-case synthetic reference drill covering signed
grants, exact mapping/grant bounds, one-use authorization, revocation,
cancellation, idempotency, fallback, uncertain outcomes, tamper rejection,
receipt semantics, rollback, and secret exclusion.

The architectural rule is explicit: a replaceable external runtime may plan or
coordinate work, but installation, runtime approval, a tool allowlist, or a
runtime's own credential system cannot create a second authority path around
Gateway -> Hypervisor -> Sandbox -> Grid.

No external runtime is loaded, no production runtime credential is resolved, no
network connection is opened, no user file is read, no external effect is
performed, and no OpenClaw, Hermes, Agent Zero, MCP, A2A, or other runtime is
certified by the synthetic reference drill.

## Current development programme

### Trust and operations

The project is collecting authentic external evidence for one controlled
single-node pilot:

- dedicated pilot hardware and 30-day availability/capacity observation;
- pilot-owned secret, provider, backup-media, telemetry, and alert custody;
- scheduled restore and rotation under that custody;
- a named-roster facilitated incident exercise;
- provider/custodian dispositions for the 32 deprecated-history credential
  candidates;
- an authentic independent security review and signed findings ledger;
- a complete reviewed pilot evidence package and separate promotion decision.

### Human utility and network activation

The parallel human-product programme remains:

- **AXIOM One** — private personal agent, vault, approvals, and receipts;
- **AXIOM Verify** — independent local/static evidence verification;
- **AXIOM Circles** — invitation-based governed collaboration;
- **AXIOM Studio** — capsule, adapter, policy, and conformance tooling;
- **AXIOM Managed Node** — optional supported operations without platform data
  ownership.

The current client contract and machine-principal foundations are implemented;
the AXIOM One browser/PWA remains experimental. A supported browser product,
bounded AI provider, useful workflows, selective sharing, Verify, Circles,
Studio, and Managed Node remain separately gated work.

### Machine interoperability substrate

Machine-principal enforcement, policy-filtered discovery, digest-only terminal
receipts, and the runtime-adapter contract now exist. The next interoperability
work is therefore no longer "add the basic machine ceilings". It is to preserve
native AXIOM authority while adding useful replaceable runtimes and protocol
edges:

1. select one maintained external runtime for a bounded read-only integration;
2. perform source, dependency, licence and threat review for that exact runtime;
3. map its invocation semantics onto the byte-pinned adapter contract without
   granting direct Grid/Hypervisor/Sandbox authority;
4. prove native authorization, cancellation, receipt, idempotency, fallback and
   uncertain-outcome parity;
5. expose MCP compatibility only after the same native authority semantics are
   retained end to end;
6. defer A2A, remote tasks, remote execution and attenuation-only delegation to
   their own multi-host and review gates.

Protocol compatibility must never create authority.

### Frontier incubation

Distributed authority, BFT, settlement, tokens, bridges, liquidity, autonomous
agents, task markets, regulated-domain systems, embodied systems,
arbitrary-code isolation, zk verification, and post-quantum migration may be
built in isolated laboratories.

Laboratory code remains disabled by default and separated from production
identities, secrets, user data, real value, and public authority. It cannot
change production or marketing status without the normal evidence gates.

> **Build broadly. Activate deliberately. Expose minimally. Promote only with evidence. Market only what is true.**

Every supported document under `docs/` on `main` is part of the canonical
current-build documentation boundary checked by `mesh/src/check-docs.mjs`.

contract drift, and computed numeric claim drift for capability, Gateway-route,
and internal-network-route counts.

## Validation

The current build must pass:

```bash
npm run setup
npm run runtime-adapter:contract
npm run runtime-adapter:drill
npm run release:verify
```

`npm run setup` installs both exact zero-dependency locks and runs the
clean-kernel and release verifiers. Protected GitHub verification additionally
runs kernel tests, container build/readiness, credential-history audit,
recovery, backup lifecycle, SLO, resilience, transport, service-unit,
node-scheduling, causal-exchange, telemetry, credential/data-key rotation,
provider conformance, pilot-verifier conformance, independent-review-verifier
conformance, incident tabletop, deny-egress checks, runtime-adapter synthetic
conformance, hosted Windows compatibility, and CodeQL analysis as applicable.

Synthetic pilot, review, runtime-adapter, and resolver fixtures prove mechanism
behavior only. They do not claim a live pilot, independent review, external
runtime certification, repository mutation, or production promotion.

Release verification binds package and lock versions, the capability and
operator registries, supported documentation, deployment inputs, migrations,
rollback, and source boundaries. A development build is not promoted merely
because those checks pass.
