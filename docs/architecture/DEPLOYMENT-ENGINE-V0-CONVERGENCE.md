## Resolve these boundaries before composing a spec

1. **Host-policy provenance and binding.** `host.profile.v1`, `contribution.policy.v1`, and `resource.sovereignty-reserve.v1` are accepted by the local host-sovereignty module, but their normalized documents have no `host_ref`, stable policy identifier, or exported digest method. `DeploymentSpec.host_policy_refs` therefore needs a reviewed way to bind a *specific* host and exact local declarations, including provenance, freshness or change handling, and a digest. Do not insert invented host fields into those exact-field contracts or accept an unbound assertion of local willingness. If applicable host evidence is unavailable or mismatched, report it as unresolved rather than selecting a provider on its behalf.
2. **Resource dimensions and observation meaning.** The Resource Envelope includes total `network_bytes`, split `durable_storage_bytes`/`scratch_storage_bytes`, and other bounded dimensions. Host contribution policy and reserve use `bandwidth_bytes_per_second`, `transfer_bytes_per_day`, `storage_bytes`, and live headroom/foreground conditions. The Resource Observation freshness selector does not supply the complete runtime state consumed by `evaluateContribution`. Decide what exact, evidence-backed mapping is valid and which checks remain unknown; do not equate rates to totals, collapse storage classes, or infer a local contribution decision from a resource envelope or observation alone.
3. **Provider evidence and downstream requests.** Define how `provider_ref` plus a canonical digest identifies a reviewed catalog entry or other accepted descriptor, and how actual host presence is evidenced independently from catalog membership. An absent host-install planner may be named only as a future *requirement* in a plan, never invoked or claimed available. Unknown provider identity, conflicting declarations, missing evidence, and incompatible host policy must fail closed; only valid equivalent candidates may remain an explicit owner choice under the approved design.
4. **Cognitive capability claims.** Where a provider binding advertises a cognitive offering, validate its `capability_ids` against the exact catalog-bound Cognitive Capability Profile and applicable observations bound to that profile, including their result and validity interval. Define an explicit mapping if the deployment capability vocabulary differs from the profile's cognitive capability vocabulary; do not accept matching strings alone as proof of an available, qualified host offering. A declared profile, an observation, or even a favorable result does not establish installation, current host presence, selection, or effect authority.

## Conservative implementation order

1. Review the exact upstream validators and source contracts above on the intended integration base; settle the host-policy binding, resource translation, and provider-evidence decisions with their owners. Keep semantic validation and JSON Schema mirrors aligned with the repository's current inert-contract patterns.
2. Add bounded `DesiredDeployment`, `DeploymentProviderBinding`, and `DeploymentSpec` contracts only after those decisions. Bind accepted inputs by exact reference and digest, reject unexpected fields and duplicate identifiers, and retain `authority_effect: "none"`, `network_effect: "none"`, `runtime_activation: false`, and `execution_authorized: false` where specified.
3. Add a deterministic, synthetic-only `DeploymentPlan` resolver and negative tests for host/digest mismatch, stale evidence, competing providers, resource conflicts, unresolved owner choices, and authority-looking inputs. Downstream installation/acquisition requests are descriptive only. Re-run documentation, status, and protected checks on the exact combined head before any separate review decision.

This note introduces no schema, installer, host mutation, provider invocation, network access, credentials, Gateway route, capability-registry change, or production promotion. A passing source-level planning test would not establish host readiness, permission to deploy, independent-hardware evidence, or a live Mesh.
