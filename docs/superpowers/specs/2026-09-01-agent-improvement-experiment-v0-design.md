# Agent Improvement Experiment v0 Design

## Status

Experimental, inert, non-production-reaching design for evidence-bound agent improvement experiments. This design does not authorize self-modification, runtime activation, model training, weight changes, or automatic promotion.

## Purpose

Agent systems can improve through many surfaces before they ever alter model weights: retrieval/context policy, memory, prompts, routing, workflow topology, skills/tools, runtime/scaffolding code, evaluators, training pipelines, adapters, and models. Existing research increasingly treats these as distinct mutable surfaces rather than reducing recursive improvement to weight updates.

The Mesh needs a local-first protocol that lets agents propose, branch, test, compare, reject, retain, and exchange improvement evidence without granting the proposing lineage authority to install its own change.

The core rule is:

> Discovery of an improvement is evidence. Evaluation of an improvement is additional evidence. Promotion remains a separate authority decision.

## Research basis

This design incorporates recurring mechanisms from current self-evolving-agent research:

- **Reflexion** demonstrates improvement through linguistic feedback and episodic memory without weight changes.
- **Promptbreeder** evolves task prompts and the mutation prompts that generate future mutations.
- **STOP** lets a language-model scaffolding program improve the scaffolding program that performs improvement.
- **Automated Design of Agentic Systems / Meta Agent Search** searches over agent programs and retains an archive of discovered architectures.
- **Darwin Gödel Machine** empirically mutates agent code and preserves a branching archive rather than replacing one canonical agent by hill-climbing only.
- **AlphaEvolve** combines model-generated candidate programs with automated evaluators and evolutionary selection.
- Recent self-evolving-agent surveys organize evolution across models, memory, tools, architecture/workflows and interaction stages, and emphasize evaluation, safety, scalability and co-evolution.
- Recent dynamic-graph work treats persistent agent evolution as graph transformation across memories, tools, skills, workflows and inter-agent relations.
- Decentralized/federated LoRA research demonstrates that later model-adaptation layers can remain local or peer-distributed rather than requiring centralized raw data, but those layers are intentionally outside v0 promotion authority.

The design intentionally adopts the strongest common lesson: **the evaluator is part of the attack surface**. A system that can change the judge and then use the changed judge as sole evidence of success can manufacture apparent progress.

## Relationship to current Mesh primitives

This design composes with existing and converging primitives rather than replacing them:

- `axiom-cognitive-selection-proposal.v1` remains proposal-only evidence about bounded candidate selection.
- agent authority ceilings and attenuation proofs remain the authority-shape mechanism for machine delegation.
- explicit subagent delegation admission remains the currentness-bound authorization precursor for child authority.
- aggregate subagent budget plans prevent parallel child spawning from multiplying explicitly shared parent budgets.
- `axiom-subagent-lineage-record.v1` binds provenance across spawned worker lineages while remaining non-authorizing.
- machine-principal effect currentness remains a late admission/effect-time recheck rather than a spawn-time-only decision.

The improvement experiment adds a new evidence domain: **what changed, why it was tried, how it was evaluated, what regressed, and whether the evidence is sufficient to recommend a separate promotion decision.**

## Scope decomposition

The implementation is split into four objects so no single object silently becomes a bearer capability.

### 1. Improvement Proposal

Schema: `axiom-agent-improvement-proposal.v1`

A proposal binds:

- proposal ID;
- origin principal/lineage evidence;
- baseline artifact/reference and digest;
- candidate artifact/reference and digest;
- exact target surface/class;
- mutation description digest;
- objective and metric/evaluator definitions;
- declared consequence class;
- experiment resource ceiling;
- rollback artifact/reference and digest;
- creation/expiry window;
- fixed non-authorizing semantics.

A proposal may be generated by an agent, human, deterministic optimizer, or imported process. Origin is provenance, not trust.

### 2. Evaluation Attestation

Schema: `axiom-agent-improvement-evaluation.v1`

An evaluation binds:

- proposal digest;
- evaluator principal ID;
- optional evaluator lineage digest;
- evaluator model/runtime/provider family descriptors as digests/IDs rather than marketing claims;
- benchmark/evaluator definition digest;
- input/evidence digest;
- metric results;
- regressions/failures found;
- verdict;
- independence facts;
- deterministic-verifier flag and evidence digest where applicable;
- signature/evaluator key identity when signed;
- fixed non-authorizing semantics.

An evaluator can attest to observations. It cannot promote the candidate simply by signing them.

### 3. Experiment Record

Schema: `axiom-agent-improvement-experiment.v1`

An experiment record binds a proposal to a canonical set of evaluation attestations and derives reproducible facts:

- number of evaluations;
- distinct evaluator principals;
- distinct lineages;
- distinct model families;
- distinct runtimes/providers where declared;
- deterministic-verifier evidence count;
- positive/negative/mixed verdict distribution;
- known regression count;
- resource observations;
- experiment status.

The experiment record must preserve negative results. A failed branch is evidence and may remain useful as a stepping stone or future disconfirming case.

### 4. Promotion Eligibility Assessment

Schema: `axiom-agent-improvement-promotion-assessment.v1`

The assessment is a pure derived decision about **eligibility to request promotion**, not promotion itself.

It binds:

- experiment digest;
- consequence profile;
- required independent evidence thresholds;
- achieved independence facts;
- rollback evidence presence;
- regression disposition;
- whether the changed surface is promotable in v0;
- recommendation: `eligible`, `ineligible`, or `insufficient-evidence`;
- reason codes;
- fixed `authority_effect=none` and `automatic_application=false` semantics.

A later governance/owner/runtime activation mechanism would consume an eligible assessment as evidence. It still must evaluate current authority and policy itself.

## Improvement surface taxonomy

Every proposal has exactly one `target_surface`:

1. `retrieval-context`
2. `memory-policy`
3. `prompt-instructions`
4. `routing-selection`
5. `workflow-topology`
6. `skill-tool`
7. `runtime-scaffolding-code`
8. `evaluator-reward`
9. `training-data-pipeline`
10. `adapter-parameters`
11. `model-weights`
12. `improvement-mechanism`

This taxonomy is deliberately substrate-neutral. A future runtime may map several surfaces to one implementation artifact, but the evidence protocol keeps their consequences distinct.

## Consequence profiles

### C0 — Contextual/reversible

Typical surfaces: retrieval/context and bounded prompt variants that disappear with the session.

Minimum recommendation evidence may be one reproducible evaluation if no external effect or persistent state change is involved.

### C1 — Persistent personal behavior

Typical surfaces: memory policy, persistent prompt/instruction configuration, routing preferences.

Requires rollback evidence plus at least one evaluation not produced solely by the candidate lineage, unless a deterministic local verifier can fully establish the relevant property.

### C2 — Agent architecture/tooling

Typical surfaces: workflow topology, new skills/tools, runtime scaffolding code.

Requires stronger regression coverage, at least one lineage-independent evaluation, and either a second independent evaluator or deterministic verifier evidence for the critical invariants.

### C3 — Measurement/evaluator mutation

Surface: evaluator/reward.

The proposed evaluator **cannot be the sole evaluator of itself**. v0 may determine eligibility only when the prior evaluator definition remains available, the candidate evaluator is evaluated against it or an independently defined oracle/test set, and independent evidence exists. Self-generated agreement does not count as independence.

### C4 — Learning/training mutation

Surfaces: training-data pipeline and adapter parameters.

v0 may record and evaluate proposals but returns `ineligible` for automatic/local promotion through this protocol. Separate training authorization, privacy/data provenance, rollback and model-evaluation infrastructure are required.

### C5 — Foundation/high-order mutation

Surfaces: model weights and improvement mechanism itself.

v0 may record experiments but must never return promotion eligibility. A later design must define substantially stronger assurance, containment, independent evaluation and governance.

## Independence model

A count of evaluators is not a count of independent evaluators.

Each evaluation contains explicit independence facts relative to the proposal origin and other evaluators:

- same lineage?
- same model family?
- same runtime implementation?
- same provider/host trust domain?
- same evaluator-definition digest?
- same benchmark/test corpus digest?
- deterministic verifier?
- human/external reviewer evidence present?

v0 does not convert these dimensions into a single mystical trust score. It derives transparent counts and uses profile-specific threshold rules.

A deterministic verifier may satisfy some independence requirements when the property is actually deterministic and the verifier evidence is locally reproducible. It does not magically establish subjective quality or truth.

## Anti-self-certification invariants

1. Proposal origin cannot itself create sufficient evidence for C2+ promotion eligibility.
2. Evaluator/reward mutation cannot use the candidate evaluator as its only judge.
3. Changing promotion thresholds is an `improvement-mechanism` mutation, not an ordinary configuration edit.
4. Candidate artifacts cannot modify historical evaluation records.
5. Negative evaluations and regression evidence cannot be omitted from a record once bound.
6. A later descendant cannot relabel an ancestor evaluation as independent merely by changing principal IDs; lineage relationships remain relevant.
7. Reputation does not substitute for proposal-specific evidence.
8. Signed provenance does not substitute for current authorization.
9. A promotion assessment never activates a candidate.
10. Rollback evidence is required before eligibility wherever persistent behavior changes.

## Local-first and decentralized operation

All v0 objects are deterministic canonical artifacts that can be created and verified locally without network access once required inputs and public keys are present.

A node owns its experiment archive. It may retain private branches indefinitely, discard local working material while retaining receipts, or selectively export an experiment/candidate/evidence bundle.

Another node may import an improvement artifact as **untrusted evidence**, reproduce the experiment locally, add its own signed evaluation, fork the candidate, or reject it. Imported popularity never grants installation authority.

This supports distributed evolutionary search without creating a global canonical agent or central update server.

## Open-ended archive semantics

The archive is a DAG rather than a single version counter. An improvement proposal may cite one or more predecessor candidate digests. A lower-scoring ancestor may remain a valid parent for future mutations.

The archive must distinguish:

- `baseline`
- `candidate`
- `evaluated`
- `rejected`
- `retained-stepping-stone`
- `eligible-for-promotion-request`
- `superseded`
- `rolled-back`

These are evidence/lifecycle states, not execution authority states.

## Resource controls

Each proposal declares an experiment ceiling for:

- maximum evaluation runs;
- maximum child agents;
- maximum tokens/cost units;
- maximum wall-clock duration;
- maximum storage bytes;
- maximum external/network effects (v0 defaults to none unless separately authorized by existing Mesh policy).

When an experiment is performed by spawned subagents, its budget must be compatible with the aggregate subagent budget plan. The experiment protocol does not mint more budget.

## Error handling / fail-closed behavior

Reject:

- unknown fields;
- unsupported schema/version;
- malformed/non-canonical timestamps;
- digest mismatch;
- duplicate evaluation IDs or evaluator identities where uniqueness is claimed;
- proposal/evaluation mismatch;
- evaluation outside proposal lifetime;
- evaluator claiming independence contradicted by supplied lineage relation;
- impossible metric values or non-canonical metric ordering;
- missing rollback artifact for persistent consequence profiles;
- promotion assessment with thresholds lower than the profile minimum;
- C4/C5 promotion eligibility;
- changed fixed semantics;
- candidate/baseline artifact identity when a mutation is claimed;
- candidate lineage trying to certify itself as lineage-independent.

## v0 nonclaims

- No runtime modification occurs.
- No model/provider/profile is switched.
- No prompt, memory or workflow is activated.
- No training or fine-tuning occurs.
- No model weights or adapters are written.
- No external network or filesystem effect is authorized.
- No globally valid reputation is created.
- No assessment proves truth, safety or universal improvement.
- No candidate is automatically promoted.
- No capability-registry promotion follows from this laboratory alone.

## Testing strategy

TDD must include at minimum:

1. valid C0 proposal/evaluation/assessment round-trip;
2. strict digest and unknown-field rejection;
3. lineage-bound origin and evaluator independence checks;
4. self-evaluation insufficient for C2;
5. deterministic verifier can satisfy an explicitly deterministic invariant requirement but not subjective-quality independence;
6. evaluator mutation rejected when candidate evaluator is sole judge;
7. negative/regression evidence preserved in experiment digest;
8. C4/C5 always ineligible in v0;
9. rollback required for C1+;
10. proposal experiment budgets cannot exceed supplied lineage/aggregate budget evidence when such evidence is bound;
11. promotion assessment cannot set `automatic_application=true` or any authority effect;
12. archive predecessor relationships are acyclic in the bounded record set under test;
13. platform-neutral deterministic serialization on Linux/macOS/Windows through the normal kernel suite.

## Follow-on work

After v0 survives adversarial review, later slices may add:

- durable local experiment archive/ledger;
- shadow/canary activation through a separate current-authority gate;
- signed Improvement Capsules for peer exchange;
- reproducible benchmark bundles;
- privacy/selective-disclosure profiles for proprietary/private experiments;
- federated/decentralized adapter learning;
- training-data lineage and consent;
- richer causal attribution of which mutation caused which performance change;
- automated rollback based on independently observed regressions;
- governance profiles for C3-C5 promotion.

None of those are implied by v0.
